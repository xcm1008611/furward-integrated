# 绒途 Furward · 自己服务器部署、备份与迁移

这份源码可独立运行：前台公开浏览，后台使用自己的密码，不需要 ChatGPT 账号、GPT API、OpenAI 密钥或 Sites 托管。本文描述白色首屏 v3 的运行与维护方法。荧光绿版本的独立备份与回滚方法见下文。

现有公网入口为 [https://8.147.109.174:8087/](https://8.147.109.174:8087/)，后台为 [https://8.147.109.174:8087/admin](https://8.147.109.174:8087/admin)。**本次网站内容更新不要求更换后台密码。** 保留现有 `.env.production`。

## 先分清程序、配置和数据

| 名称 | 包含什么 | 维护方式 |
| --- | --- | --- |
| 源码 ZIP / Docker 镜像 | 网站程序、默认素材、部署工具 | 更新或回滚程序时使用 |
| `.env.production` | 密码校验值、会话签名密钥等配置 | 私下单独备份，不能公开 |
| 数据目录 / 命名卷 | 已保存内容与上传图片 | 更新前做完整备份，不能删除 |

源码目录与服务器 Compose 项目保留 `lando-studio` 名称。现有服务器的命令统一带 **`-p lando-studio`**，继续使用同一个 `lando-data` 持久卷，容器内路径是 `/app/data`。

**不要运行 `docker compose ... down -v`，不要删除既有卷，也不要把项目名改成 Furward 后直接启动一套空卷。** 换品牌名称不需要换数据卷。

以下 Docker 命令在现有 `compose.yml` 所在目录执行；新服务器可把源码放在 `/opt/lando-studio`。源码 ZIP 本身不包含运行数据库、上传图片或管理员配置。

## 新服务器方法一：Docker

先安装 Docker Engine 与 Compose，确认可运行 `docker --version`、`docker compose version`。解压源码，进入 `lando-studio` 文件夹。

### 首次设置密码

已有服务器跳过这一步，保留原配置。新安装可用临时 Node 24 容器设置密码，不需要在宿主机另装 Node：

```sh
docker run --rm -it \
  --user "$(id -u):$(id -g)" \
  -v "$PWD:/workspace" -w /workspace \
  node:24-bookworm-slim node scripts/setup-admin.mjs
```

工具允许自选密码或随机生成，写入 `.env.production` 和 `.admin-credentials`，权限为仅当前用户可读写。已有文件时会拒绝覆盖。登录信息只留给管理员，不加入源码包，也不发给普通访客。

### 构建和启动

```sh
docker compose -p lando-studio up -d --build
docker compose -p lando-studio logs --tail=50
```

默认绑定服务器本机 `127.0.0.1:3000`，外部访问通过 HTTPS 代理。命名卷在容器重建后继续保留。日常命令：

```sh
docker compose -p lando-studio ps
docker compose -p lando-studio logs --tail=100
docker compose -p lando-studio restart web
```

暂时停站用 `docker compose -p lando-studio stop web`，重新启动用 `docker compose -p lando-studio up -d`。

## 新服务器方法二：Node 24

安装 Node.js 24，运行 `node --version` 确认显示 `v24...`。本项目使用 Node 内置 SQLite，不能直接换成旧 Node 运行。

```sh
npm ci
npm run setup:admin
npm run build:selfhost
BIND_ADDRESS=127.0.0.1 PORT=3000 npm run start:selfhost
```

已有 `.env.production` 时跳过 `setup:admin`。保持生产进程运行，网站才会在线。开发预览使用：

```sh
npm run dev:selfhost -- --port 3000
```

本机前台是 `http://localhost:3000`，后台是 `http://localhost:3000/admin`。本机数据和公网数据互相独立，不会自动同步。

导出源码 ZIP 中的默认 `dev`、`build`、`start` 已指向独立 Node 方式，`:selfhost` 别名仍保留。原开发工作区另有托管适配命令，所以这份文档统一写 `:selfhost`。

### 需要开机自动运行时

可配置 systemd。以下仅是模板，先替换用户和路径，并用 `which npm` 核对可执行文件：

```ini
[Unit]
Description=Furward website
After=network.target

[Service]
Type=simple
User=lando
WorkingDirectory=/opt/lando-studio
Environment=NODE_ENV=production
Environment=BIND_ADDRESS=127.0.0.1
Environment=PORT=3000
ExecStart=/usr/bin/npm run start:selfhost
Restart=on-failure
RestartSec=5
UMask=0077

[Install]
WantedBy=multi-user.target
```

保存为 `/etc/systemd/system/lando-studio.service` 后：

```sh
sudo systemctl daemon-reload
sudo systemctl enable --now lando-studio
sudo systemctl status lando-studio
```

Node 更新时先备份，再运行 `npm ci`、`npm run build:selfhost`，最后 `sudo systemctl restart lando-studio`。

## HTTPS 与代理设置

现有 `https://8.147.109.174:8087/` 保持现有端口和代理配置即可。新域名部署可把域名解析到服务器，再由 Caddy、Nginx 或服务器面板代理到 `127.0.0.1:3000`。

Caddy 示例：

```caddyfile
your-domain.com {
    reverse_proxy 127.0.0.1:3000
}
```

Nginx 的 HTTPS `server` 中，代理位置可按以下方式保留真实访问地址：

```nginx
location / {
    proxy_pass http://127.0.0.1:3000;
    proxy_set_header Host $http_host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
}
```

其中 `Host` 保留域名和访问端口，`X-Forwarded-Proto` 由代理覆盖为实际协议，不能拼接客户端传来的多个值。后台用它们判断同源请求，并在 HTTPS 下设置安全 Cookie。不要为了让登录通过而允许任意来源。

管理员配置和数据目录不能作为静态文件对外发布。新域名还需要证书与相应端口放行；现有服务器不要覆盖其他站点的代理配置。

## 配置与密码维护

| 参数 | 作用 |
| --- | --- |
| `ADMIN_PASSWORD_HASH` | 密码的校验值，不是登录时输入的明文密码 |
| `ADMIN_SESSION_SECRET` | 登录 Cookie 签名密钥，改变后旧登录失效 |
| `DATA_DIR` | Node 数据目录，默认 `./data`；Docker 固定 `/app/data` |

首次设置工具自动生成正确格式。更新 Furward 内容无需重设这两个登录参数。

确实需要换密码时，先单独备份当前配置，再生成新文件：

```sh
node scripts/setup-admin.mjs \
  --output .env.admin-new \
  --credentials-file .admin-credentials-new
```

把新文件中的两个登录参数更新到现有 `.env.production`，保留其他配置，然后重启服务。Docker 用户可在前面的临时 Node 容器命令末尾添加同样的参数。文件已存在就换新文件名，不覆盖原件。

## 完整备份

数据目录包含 `content.sqlite` 和 `uploads/`。SQLite 运行中可能还有 `-wal`、`-shm` 文件，不要在仍有写入时只复制一个数据库文件。下列工具会生成一致的数据库快照并复制上传图片。

后台「下载备份」只导出内容 JSON，不能代替这里的完整备份。开始备份前先结束后台编辑，避免备份期间继续上传。

### Node

```sh
npm run backup:selfhost -- ./backups/before-update-20261024
```

### 现有 Docker 服务器

```sh
docker compose -p lando-studio exec web \
  node scripts/selfhost-backup.mjs /app/data/backups/before-update-20261024
mkdir -p backups
docker compose -p lando-studio cp \
  web:/app/data/backups/before-update-20261024 ./backups/before-update-20261024
```

每次使用新的目录名，工具不会覆盖已有目录。把整个备份目录再复制到另一台机器或备份盘。只留在同一块服务器硬盘上不能防止整台服务器丢失。

本次白色版更新前，荧光绿首屏完整版本已保存：

| 内容 | 已保留的位置 / 标识 |
| --- | --- |
| 源码 Git 标签 | `furward-fusion-v1-20261024` |
| 服务器 Docker 镜像 | `lando-studio-web:furward-fusion-v1-20261024` |
| 完整内容与上传备份 | `/app/data/backups/furward-fusion-v1-20261024` |
| 容器之外的私有独立目录 | `/opt/lando-studio/backups/furward-fusion-v1-20261024/` |

私有独立目录包含 `source.zip`、`data/` 和 `.env.production`。不要把它放入静态网站目录、公开下载链接或源码交付包。本文只记录位置，不读取或记录配置值。更早的 `before-furward-20261024` 备份也继续保留，它对应的是更早一代网站，不要和本轮荧光绿版本混用。

登录配置不在内容备份中：`.env.production` 请另外私下保管，或在新服务器重新设置密码。

## 从旧内容迁移到 Furward v3

v3 对应白色首屏。本交付包的前台默认显示拉布拉多，点击「播放演示」后在约 6 秒内经过流动视角并停留在机器狗画面，支持暂停、继续和重播。后台提供两个独立素材槽，以及叠加对齐和可暂停的流动预览。第二屏起继续保留现有布局和滚动动效。

新版默认图片包括 6 张人物位于盲道的场景，以及 3 张宠物被毛概念：麦穗暖金短毛、云团奶白长毛、暮灰烟灰顺毛。新图片使用 `/reference/furward-v3/` 路径；原始人物透明图、机器狗产品图和温暖主图仍保留原路径，上传素材不删除。

迁移规则区分两种来源：

- **v2 荧光绿 Furward**：逐字段比较冻结的旧默认值，只升级尚未修改的默认文字、图片和说明。用户自定义文案、上传图、额外图片、位置、大小和显示开关继续保留。
- **v1 更早的旧站**：使用 Furward 默认内容展示，完整旧 JSON 和自定义差异保留备份；旧图片不会自动填入含义不同的新槽位，需人工挑选用途。

普通读取只做内存转换，不写原数据库。第一次保存 v3 时，原始 JSON 按实际来源保存为私有记录，例如 `furward-legacy-v2-revision-N`；其中 `N` 是原内容保存版本号。旧 v1 备份记录也继续保留。后台草稿改用独立的 `furward-content-draft-v3`，API 拒绝 v1、v2 旧格式直接覆盖新内容。

正式更新时先做前面的完整备份，再用**已包含 v3 代码的新容器**执行内容审核。下面命令只访问内容数据库，不需要读取管理员密码。

### 先审核，不改数据库

```sh
docker compose -p lando-studio exec web \
  node scripts/furward-migrate.mjs \
  --data-dir /app/data \
  --output /app/data/backups/furward-v3-review-20261024
```

输出目录包含：

- `source-original.json`：原始内容，不做格式改写。
- `source-snapshot.json`：原内容及保存版本号。
- `furward-content.json`：建议使用的 v3 内容。
- `migration-review.json`：迁移来源、自定义差异、保留的上传引用与归档栏目。

v2 的审核清单会标记自定义内容是继续保留在新内容中，还是只保留在原始备份中；正常后台可编辑的文字、图片和构图会继续保留。v2 原有字段不会因为新增于上一代就误判成 v1 自定义内容。

### 审核后保存迁移

确认差异清单后，使用另一个新输出目录：

```sh
docker compose -p lando-studio exec web \
  node scripts/furward-migrate.mjs \
  --data-dir /app/data \
  --output /app/data/backups/furward-v3-applied-20261024 \
  --apply --reviewed
```

`--apply` 才会写入数据库；检测到自定义差异时，需要先审核并加 `--reviewed`。未修改的 v2 默认内容不会产生自定义差异。另一后台窗口同时保存时，版本检查会拒绝覆盖，需要重新读取与审核。重复执行已完成的 v3 迁移不会再增加保存版本，素材文件不会被删除。

Node 运行方式相同，把 `--data-dir /app/data` 改成实际数据目录，例如 `--data-dir ./data`。也可对导出的内容快照只生成审核文件：

```sh
node scripts/furward-migrate.mjs \
  --input ./content.json \
  --output ./backups/furward-v3-review
```

迁移工具需要 Node 24，不依赖额外 npm 包；生产构建会带上需要的脚本与内容文件，包括不可修改的 `lib/furward-v2-defaults.ts` 基线。不要为了更新默认文案去修改这份历史快照。

旧路由在新程序中继续重定向：`/on-track` → `/#scenes`、`/off-track` → `/#companion`、`/calendar` → `/#technology`。旧三内页不会重新显示。

## 恢复到空库，或恢复同版本备份

先准备完整备份目录。恢复时停止网站，避免边写边恢复。默认仅允许空数据库；明确替换已有数据时才加 `--replace`，工具会先备份被替换的现状。

Node：

```sh
npm run restore:selfhost -- ./backups/before-update-20261024
```

Docker 先把备份复制进现有卷，再停止服务并恢复：

```sh
docker compose -p lando-studio cp \
  ./backups/before-update-20261024 web:/app/data/restore-input-20261024
docker compose -p lando-studio exec --user root web \
  chown -R node:node /app/data/restore-input-20261024
docker compose -p lando-studio stop web
docker compose -p lando-studio run --rm --no-deps web \
  node scripts/selfhost-restore.mjs /app/data/restore-input-20261024
docker compose -p lando-studio up -d
```

已有内容需要明确替换时，在恢复脚本命令最后加 `--replace`。完成后检查文字、图片和后台登录。不要删除卷来实现“恢复”。

已有内容快照包若包含 `content.json` 与 `uploads/`，可用 `--from-content` 导入：

```sh
npm run restore:selfhost -- --from-content ./migration
```

这也只默认导入空库；不是源码自动同步。旧快照在新版程序里会经过 v3 升级，因此保留原始快照，并先用迁移审核工具核对自定义内容。

## 恢复完整荧光绿版本

**回滚需要匹配的程序和数据。** 单独把 v2 JSON 交给 v3 新程序，它仍会升级到白色版；只切换 Git 标签也不会自动恢复服务器数据。

本轮已保留的荧光绿版本是 Git 标签 `furward-fusion-v1-20261024`、镜像 `lando-studio-web:furward-fusion-v1-20261024`，以及完整数据备份 `/app/data/backups/furward-fusion-v1-20261024`。管理员还可从私有独立目录 `/opt/lando-studio/backups/furward-fusion-v1-20261024/` 恢复源码与配置。配置文件不在公开源码 ZIP 中。

回滚前，先用「完整备份」一节的方法备份当前新版数据，使用新的目录名，例如 `before-white-rollback-20261024`。然后在现有项目目录写一份临时覆盖配置 `compose.rollback.yml`：

```yaml
services:
  web:
    image: lando-studio-web:furward-fusion-v1-20261024
```

使用同一 Compose 项目、同一数据卷，让旧程序恢复与它匹配的备份：

```sh
docker compose -p lando-studio stop web
docker compose -p lando-studio -f compose.yml -f compose.rollback.yml \
  run --rm --no-deps web node scripts/selfhost-restore.mjs \
  /app/data/backups/furward-fusion-v1-20261024 --replace
docker compose -p lando-studio -f compose.yml -f compose.rollback.yml \
  up -d --no-build
```

恢复工具会在替换前另外保留现状。回滚后检查荧光绿首屏、已保存文字、上传图片和后台登录。回滚期间继续使用覆盖配置，避免下一次误启动新镜像。保留 `.env.production`、项目名和命名卷；密码配置无需随内容回滚。

更早的 `lando-studio-web:before-furward-20261024` 镜像与 `before-furward-20261024` 数据备份对应更早的旧站，不能拿来代替本轮荧光绿快照。不要运行带 `-v` 的删除卷命令来恢复网站。

## 源码导出与维护检查

```sh
npm run export:source
node --test scripts/furward-test.mjs scripts/test-cms.mjs scripts/test-admin.mjs
npm run test:selfhost
```

源码 ZIP 保存到 `outputs/`，顶层目录仍为 `lando-studio/`。它不包含 `.env.production`、密码信息、数据卷、上传图片或旧备份。把源码交给新维护者时，运行数据和管理员配置应分别交接。

| 情况 | 优先检查 |
| --- | --- |
| 后台提示尚未配置 | 新服务器是否设置过密码；现有服务器是否保留并加载了原配置 |
| 登录返回来源不一致 | 代理是否保留带端口的 Host，并覆盖为单个正确的 X-Forwarded-Proto |
| 登录后又回到登录页 | HTTPS、代理协议、浏览器 Cookie 是否正常 |
| 上传失败 | 登录是否过期、文件是否超过 10 MB、数据目录是否可写 |
| 重启后内容像全新网站 | DATA_DIR、Compose 项目名和命名卷是否误换了 |
| 旧草稿保存被拒绝 | 使用新版后台重新编辑；先保留旧草稿备份，不要强行改版本号 |
| 恢复后仍是白色首屏 | 使用了 v3 程序的升级逻辑；回滚荧光绿版需使用上述 v2 镜像与对应数据备份 |
